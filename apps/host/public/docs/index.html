    vue-mfe-vite

    A complete, working Vue 3 + Vite 7 micro-frontend monorepo built with Module Federation.

    📖 Online docs: Vue MFE Vite Docs (every guide in one page) · Migrating a Vue 3 project to Vite 7? Start with the Migration kit: packages & versions. · Local copy: npm run docs:build, then open docs/site/index.html or Docs ↗ in the host header.

    App Role Port Exposes / consumes Theme
    apps/host Container: routing, login, layout, header, ui-dev library 8080 consumes shellA/App, shellB/App; exposes ./ui-dev green
    apps/shell-a Remote: product catalog + cart 8081 exposes ./App; consumes host/ui-dev indigo
    apps/shell-b Remote: task board 8082 exposes ./App; consumes host/ui-dev teal

    #What's inside

    • Vite 7 (vite@^7.3) with @vitejs/plugin-vue@6
    • Plain JavaScript as .mjs everywhere (configs, scripts, source). No TypeScript, no generated .d.ts
    • vite.config.mjs driven by .env.[mode] through each app's config/env.mjs (ports, URLs, CORS, sourcemaps, remote entries)
    • shared.federation.json in each remote: the federation contract (exposes, remotes, shared), turned into plugin options by config/federation.mjs
    • ui-dev shared UI library owned by the host and federated to the remotes as host/ui-dev (<UiButton>, <UiCard>, <UiInput>, …, auto-resolved, no imports)
    • Module Federation via @module-federation/vite (works in dev and build)
    • Sass (modern compiler API) with per-app design tokens injected through additionalData
    • Critical CSS inline in each index.html (background + boot splash before JS loads)
    • Auto import: unplugin-auto-import (vue, vuex, vue-router, own composables, lodash-es as _) and unplugin-vue-components (no manual component registration)
    • Vuex 4: one independent store per app, each installed/provided under its own injection key
    • axios: one private instance per app (own baseURL, timeout, interceptors, own API gateway key) and not shared through federation
    • Mock API with gateway-key verification (axios adapter): host login, shell-a products, shell-b todos. npm run check:env verifies keys for every app and mode
    • Sample login in the host (route guard, session in sessionStorage)
    • Cross-app communication with a tiny window CustomEvent bus (mfe:*) instead of shared state
    • Per-app env files for development / localprod / staging / production
    • Offline fixtures, so the demo still works behind a proxy with no internet

    #Troubleshooting

    Symptom Fix
    "Shell A is unavailable" card in the host The remote isn't running. npm run dev at the root starts all apps. Check VITE_SHELL_A_ENTRY.
    Standalone remote shows nothing / RUNTIME-008 for :8080/remoteEntry.js Remotes load host/ui-dev from the host. Start the host too (npm run dev starts all three).
    missing env for mode "…" on start Add the listed keys to .env.[mode] of that app (see .env.example).
    GET http://localhost:5000/ 403 (Forbidden) on macOS macOS AirPlay Receiver owns port 5000. This repo now uses 8080–8082; or disable AirPlay Receiver in System Settings.
    Blocked request. This host is not allowed Add the host name to VITE_ALLOWED_HOSTS in that app's .env.[mode].
    Port already in use Ports are strictPort. Free 8080–8082 or change VITE_PORT (and the host's VITE_SHELL_*_ENTRY).
    Remote chunks 404 in production The remote's VITE_PUBLIC_URL (build base) must be the URL it is deployed at.
    Products / tasks show fixture data The public APIs (dummyjson / jsonplaceholder) were unreachable; the services fell back to src/services/fixtures.
    Unsupported engine / Vite won't start Upgrade Node to 20.19+ or 22.12+.

    Module Federation: complete developer guide

    Everything you need to set up, configure, extend and debug Module Federation in this repo: concepts, a from-scratch setup, every plugin option, every config method with its complete shape and when to use it, copy-paste snippets, and a fix for every runtime / build error code.

    Versions used here: @module-federation/vite 1.23, Module Federation runtime 2.x (@module-federation/runtime-core), Vite 7, Vue 3.5.

    #1. Concepts in 2 minutes

    Term Meaning In this repo
    Container A build that takes part in federation. Every app is one. host, shellA, shellB
    Remote A container that exposes modules to others. shell-a, shell-b (expose ./App), host (exposes ./ui-dev)
    Host / consumer A container that loads modules from remotes. host (loads shellA/App, shellB/App), remotes (load host/ui-dev)
    remoteEntry.js A remote's small manifest + bootstrap file. Hosts fetch it first. http://localhost:500x/remoteEntry.js
    Expose A public module path → a file. Imported as <remote>/<path>. './App' → ./src/expose/App.mjs
    Share scope A runtime registry of shared packages (default name default). vue lives there
    Shared dependency A package that every container agrees to load once. vue (singleton)
    Share strategy How versions are negotiated: version-first (fetch all remotes first) or loaded-first (use what's already loaded). loaded-first

    A container can be host and remote at the same time. Here federation goes both ways:

    text
    host ──imports──► shellA/App ──imports──► host/ui-dev
     ──imports──► shellB/App ──imports──► host/ui-dev

    #What happens at runtime (host page)

    1. The browser loads the host's index.html. The plugin injects a host init script that creates the federation runtime instance and registers shellA, shellB and the shared vue.
    2. The user opens /shell-a. ShellAView calls import('shellA/App').
    3. The runtime fetches VITE_SHELL_A_ENTRY (remoteEntry.js), calls its init() with the share scope (so shell-a reuses the host's vue), then get('./App').
    4. ./App is src/expose/App.mjs. It awaits host/ui-dev (the runtime fetches the host's own remoteEntry.js, which is cached), then returns App.vue.
    5. Vue renders <App :user> inside the host's app instance. Shell-a's CSS is injected (bundleAllCSS).

    #2. Setup from scratch

    #2.1 Install

    bash
    npm i -D @module-federation/vite vite@^7 @vitejs/plugin-vue
npm i vue

    #2.2 A remote (expose a component)

    js
    // apps/shell-a/vite.config.mjs (simplified)
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import { federation } from '@module-federation/vite'

export default defineConfig(({ command }) => ({
  base: command === 'build' ? 'http://localhost:8081/' : '/', // absolute in production!
  plugins: [
    vue(),
    federation({
      name: 'shellA',
      filename: 'remoteEntry.js',
      exposes: { './App': './src/expose/App.mjs' },
      shared: { vue: { singleton: true, requiredVersion: '^3.5.0' } },
      bundleAllCSS: true,
      dts: false,
    }),
  ],
  server: { port: 8081, strictPort: true, origin: 'http://localhost:8081', cors: true },
  preview: { port: 8081, strictPort: true, cors: true },
  build: { target: 'esnext' }, // runtime uses top-level await
}))

    In this repo the federation({...}) options come from apps/shell-a/shared.federation.json (see VITE_CONFIG.md).

    #2.5 Checklist for a new remote

    1. Pick a unique name (valid JS identifier: shellC, not shell-c).
    2. filename: 'remoteEntry.js', exposes, shared: { vue: { singleton: true } }.
    3. Absolute base for builds (VITE_PUBLIC_URL) and server.origin for dev.
    4. CORS: allow the host origin (VITE_CORS_ORIGINS).
    5. build.target: 'esnext'.
    6. In the host: add the remote with type: 'module', add its URL to every .env.[mode].
    7. Add the remote's origin to the host's VITE_CORS_ORIGINS if it uses host/ui-dev.

    #3. Plugin options reference (federation({...}))

    Option Type Default What it does This repo
    name string (required) Container name. Unique per page, valid identifier. Hosts reference remotes by it. host, shellA, shellB
    filename string 'remoteEntry.js' File name of the remote entry emitted at the build root. remoteEntry.js
    exposes Record<string, string | { import }> {} Public paths → source files. Keys start with ./. ./App, ./ui-dev
    remotes Record<string, string | RemoteObject> {} Remotes this container consumes. Prefer the object form. host: shellA, shellB; remotes: host
    shared string[] | Record<string, string | SharedConfig> {} Packages loaded once and shared. vue
    shareScope string | string[] 'default' Default share scope name for this container. default
    shareStrategy 'version-first' | 'loaded-first' 'version-first' version-first fetches every remote entry at startup to pick the best version. loaded-first reuses what's loaded and fetches remotes lazily. loaded-first
    bundleAllCSS boolean false Adds all CSS of the build to every exposed module, so the consumer gets your styles. true everywhere
    publicPath string Vite base (or auto) Override the public path used for remote chunks. not set (we use base)
    getPublicPath string – JS expression evaluated at runtime to compute the public path (e.g. from window). –
    varFilename string – Also emit a var-format entry for webpack/rspack hosts. –
    manifest boolean | { fileName, filePath, disableAssetsAnalyze, additionalData } false Emit mf-manifest.json + mf-stats.json (lets hosts load a remote by manifest URL, enables preloading). –
    dts boolean | object on Generate/consume federated TypeScript types. Needs a tsconfig.json. false (no TS)
    dev boolean | { disableLiveReload, disableHotTypesReload, … } on Dev-time helpers (live reload, hot types). default
    runtimePlugins Array<string | [string, options]> [] Paths to runtime plugins (hooks around loading, see §6.4 and §4.6). –
    hostInitInjectLocation 'html' | 'entry' 'html' Where the host init script is injected. Use 'entry' for apps without index.html (SSR). default
    moduleParseTimeout number (s) 10 Max time to parse modules during build. default
    moduleParseIdleTimeout number (s) – Idle timeout (resets on activity). Better for big builds. –
    virtualModuleDir string '__mf__virtual' Folder for generated virtual modules. default
    ignoreOrigin boolean false Don't rewrite asset origins. –
    target 'web' | 'node' 'web' Build target for tree shaking. –
    disableRemote / disableShared / disableSnapshot boolean false Strip unused runtime features to save bytes. Only when you're sure. –
    ssrFilename, ssrExternals, ssrEntryLoader – – SSR builds only. –
    library, runtime, implementation – – Advanced / webpack-compat. Leave unset. –
    experiments { externalRuntime, provideExternalRuntime, hostProvidesAllShared, ssrMode } – Experimental features (single shared runtime, import-map sharing). –

    #3.1 Remote object (remotes.<key>)

    Field Required Description
    type recommended 'module' for Vite (ESM) remotes. 'var' for webpack/rspack global-format remotes. Omitting it defaults to 'var' with a warning.
    name ✅ The remote's container name.
    entry ✅ URL of remoteEntry.js (or mf-manifest.json when the remote emits a manifest).
    entryGlobalName for var Global variable name of a var container. Keep it equal to name.
    shareScope – Share scope(s) used with this remote.
    internalName – Override the internal container name (rare).

    String shorthand (webpack style) also works for var remotes: shellA: 'shellA@https://…/remoteEntry.js'.

    #3.2 Shared config (shared.<package>)

    Field Type Description
    singleton boolean Only one copy may exist on the page. Required for vue.
    requiredVersion string | false Semver range this container accepts ('^3.5.0'). A mismatch logs a warning (or throws with strictVersion).
    strictVersion boolean Throw instead of warning on a version mismatch.
    version string Version this container provides (defaults to the installed one).
    eager boolean Bundle the share into the entry chunk instead of loading it async. Avoid unless needed.
    import string | false false = don't bundle a fallback, the host must provide it (else RUNTIME-012).
    shareScope string Put this share in a non-default scope.
    shareKey / request string Register under a different key / import request.
    allowNodeModulesSuffixMatch boolean Match copies installed in nested node_modules (monorepos).
    suppressMissingImportWarning boolean Silence the warning for import: false shares.
    treeShaking { mode, usedExports } Experimental shared tree shaking.

    Rule of thumb for Vue MFEs: share vue as a singleton. Share vue-router / pinia / vuex only if the remote must use the host's instance. In this repo they are not shared on purpose, because every app owns its store and HTTP client.

    #4. Config methods, complete shapes & when to use what

    This section answers three questions:

    1. How can federation be configured? (seven methods, with a snippet each)
    2. What is the complete shape of every config object, at build time and at runtime?
    3. When should you use which method / option? (decision tables in §4.7)

    Shapes below are taken from the installed type definitions (@module-federation/vite/lib/*.d.ts, @module-federation/runtime-core/dist/type/*.d.ts), written as plain JS objects because this repo has no TypeScript.

    #4.1 The configuration methods at a glance

    # Method Where it lives Resolved at This repo
    A Inline object in vite.config.mjs federation({...}) build / dev start host
    B Dedicated config module + createModuleFederationConfig() module-federation.config.mjs build / dev start – (alternative to A)
    C JSON contract + builder function shared.federation.json + config/federation.mjs build / dev start shell-a, shell-b
    D Env-driven URLs (.env.[mode]) .env.development, .env.production, … build / dev start all apps (combined with A/C)
    E Manifest-based remotes remote emits mf-manifest.json, host points entry at it runtime (fetch) –
    F Runtime API (registerRemotes, createInstance, loadRemote) app code runtime – (snippets §4.5)
    G Runtime plugins runtimePlugins: ['./src/mf/x.mjs'] runtime hooks – (snippets §4.6)

    A–D decide what is compiled in. E–G decide what happens in the browser. Real apps mix them: this repo is C + D for remotes and A + D for the host.

    #Method A: inline object (host)

    Smallest setup. Everything is visible in one file.

    js
    // apps/host/vite.config.mjs (simplified)
import { federation } from '@module-federation/vite'

export default defineConfig(({ mode }) => {
  const env = readEnv(mode, root)
  return {
    plugins: [
      vue(),
      federation({
        name: 'host',
        filename: 'remoteEntry.js',
        exposes: { './ui-dev': './src/ui-dev/index.mjs' },
        remotes: {
          shellA: { type: 'module', name: 'shellA', entry: env.raw.VITE_SHELL_A_ENTRY },
          shellB: { type: 'module', name: 'shellB', entry: env.raw.VITE_SHELL_B_ENTRY },
        },
        shared: { vue: { singleton: true, requiredVersion: '^3.5.0' } },
        bundleAllCSS: true,
        shareStrategy: 'loaded-first',
        dts: false,
      }),
    ],
  }
})

    #Method B: dedicated config module with createModuleFederationConfig

    createModuleFederationConfig(options) returns options unchanged. It exists for editor autocompletion (JSDoc / types) and to keep the federation contract in its own file, which other tools (scripts, tests, docs generators) can import without loading Vite.

    js
    // apps/host/module-federation.config.mjs
import { createModuleFederationConfig } from '@module-federation/vite'

/** @param {Record<string, string>} env */
export default (env) =>
  createModuleFederationConfig({
    name: 'host',
    filename: 'remoteEntry.js',
    exposes: { './ui-dev': './src/ui-dev/index.mjs' },
    remotes: {
      shellA: { type: 'module', name: 'shellA', entry: env.VITE_SHELL_A_ENTRY },
    },
    shared: { vue: { singleton: true, requiredVersion: '^3.5.0' } },
    dts: false,
  })
    js
    // apps/host/vite.config.mjs
import mfConfig from './module-federation.config.mjs'
// …
plugins: [vue(), federation(mfConfig(env.raw))]

    #Method C: JSON contract + builder (remotes)

    A JSON file holds the static contract (name, exposes, remotes, shared). A small builder turns it into plugin options, injects env URLs and enforces rules. JSON can't hold functions or env values, which is exactly why it is a good contract: it is reviewable and tool-readable (CI can diff exposes, a portal can list remotes).

    json
    // apps/shell-a/shared.federation.json
{
  "name": "shellA",
  "filename": "remoteEntry.js",
  "exposes": { "./App": "./src/expose/App.mjs" },
  "remotes": { "host": { "type": "module", "entryEnv": "VITE_HOST_ENTRY" } },
  "shared": { "vue": { "singleton": true, "requiredVersion": "^3.5.0" } },
  "notShared": { "axios": "own instance", "vuex": "own store" },
  "bundleAllCSS": true,
  "shareStrategy": "loaded-first"
}
    js
    // apps/shell-a/vite.config.mjs
import { loadFederationJson, createFederationOptions } from './config/federation.mjs'
const fed = loadFederationJson(root)
// …
plugins: [vue(), federation(createFederationOptions(fed, env.raw, pkg))]

    createFederationOptions (in config/federation.mjs) maps entryEnv → URL, defaults type: 'module', fails the build if a shared package is missing from package.json, and fails if a package is both shared and notShared.

    #Method D: env-driven URLs

    Never hard-code remote URLs. Put one key per remote in every .env.[mode] and read it in the config. scripts/check-env.mjs fails npm run dev / build when a key is missing or not an absolute URL.

    ini
    # apps/host/.env.staging
VITE_SHELL_A_ENTRY=https://shell-a.staging.example.com/remoteEntry.js
VITE_SHELL_B_ENTRY=https://shell-b.staging.example.com/remoteEntry.js

    Changing a URL needs a rebuild of the consumer. If that's not acceptable, use E or F.

    #Method E: manifest-based remotes

    The remote emits mf-manifest.json (its exposes, shared deps, assets per expose). The host points entry at the manifest instead of remoteEntry.js. The runtime reads the manifest, then loads the real entry. Benefits: preloading of an expose's JS and CSS, DevTools graph, version info, and the remote can rename its entry file without touching hosts.

    js
    // remote
federation({ name: 'shellA', manifest: true /* or { fileName: 'mf-manifest.json' } */ })

// host
remotes: {
  shellA: { type: 'module', name: 'shellA', entry: 'https://shell-a.example.com/mf-manifest.json' },
}

    #Method F: runtime API (URLs known only in the browser)

    For remotes discovered at runtime: per-tenant URLs, a /config.json fetched at boot, feature-flagged remotes, plugin marketplaces. See full snippets in §4.5.

    js
    import { registerRemotes, loadRemote } from '@module-federation/runtime'

const cfg = await fetch('/config.json').then((r) => r.json())
registerRemotes([{ name: 'shellC', type: 'module', entry: cfg.shellCEntry }])
const { default: ShellC } = await loadRemote('shellC/App')

    #Method G: runtime plugins

    Change how things load without changing what loads: retries, fallbacks, auth headers on manifest fetches, URL rewriting, logging. Declared at build time, run in the browser.

    js
    federation({ /* … */ runtimePlugins: ['./src/mf/retry-plugin.mjs', ['./src/mf/log.mjs', { level: 'debug' }]] })

    The tuple form [path, options] passes options to the plugin's default-export factory.

    #4.2 Complete shape: federation(options) (build time)

    Every key the Vite plugin accepts, with its default. Omit anything you don't need.

    js
    federation({
  // ── identity ─────────────────────────────────────────────────────────────
  name: 'shellA',                       // REQUIRED. Unique per page, valid JS identifier
  filename: 'remoteEntry.js',           // remote entry file name (default 'remoteEntry.js')
  varFilename: undefined,               // e.g. 'varRemoteEntry.js': extra entry for webpack/rspack hosts

  // ── what this container offers ───────────────────────────────────────────
  exposes: {
    './App': './src/expose/App.mjs',              // string form
    './routes': { import: './src/expose/routes.mjs' }, // object form
  },

  // ── what this container consumes ─────────────────────────────────────────

    #Which configuration method?

    Situation Use Why
    One or two apps, small team A inline Least indirection.
    Config is long, or scripts/tests need to read it without Vite B createModuleFederationConfig Separate, importable, autocompletion.
    Many remotes, platform team reviews contracts, CI diffs exposes C JSON contract + builder Static, tool-readable, rules enforced in one place. Used for shell-a/shell-b.
    URL differs per environment, a rebuild per environment is fine D env vars Simple, validated by check:env. Used everywhere here.
    Need preloading of JS+CSS, DevTools graph, version info E manifest Richer metadata than remoteEntry.js.
    Same build deployed to many environments/tenants, URL decided at boot F runtime registerRemotes No rebuild to move a remote.
    Cross-cutting behaviour (retry, fallback, CSP, auth, logging) G runtime plugin Keeps loading policy out of components.

    #How to load a remote module

    Need Use
    Route-level page, remote declared in config component: () => import('shellA/App') (lazy route)
    Component inside a page, with loading/error UI defineRemoteComponent(() => import('shellA/App')) (src/utils/defineRemoteComponent.mjs, wraps defineAsyncComponent)

    #type: 'module' vs 'var'

    Remote built with type
    Vite (@module-federation/vite) 'module'
    webpack 5 / rspack, library.type: 'var' (default) 'var' + entryGlobalName
    webpack/rspack with library: { type: 'module' } 'module'
    Vite remote consumed by a webpack host remote adds varFilename, webpack host uses name@url/varRemoteEntry.js

    #shareStrategy

    Use When
    'loaded-first' Default choice for Vite MFEs. Remotes load lazily; standalone remotes don't fetch other remotes at startup. Used here.
    'version-first' Several remotes ship different versions of a shared lib and you need the highest compatible version picked up front. Costs: all remote entries are fetched at startup, and one offline remote slows boot.

    #Shared options

    Option Use when Avoid when
    singleton: true Library holds global state or identity checks (vue, vue-router if shared, pinia) Pure utilities (lodash): multiple copies are harmless
    requiredVersion Always for singletons, so mismatches are visible –
    strictVersion: true A mismatch would break at runtime (major versions) You prefer a warning and a working page
    eager: true A module reads the shared lib at evaluation time in the entry chunk and you can't make it async Normally: it inflates the entry and disables negotiation for that lib
    import: false Host guarantees it provides the lib (remote never runs standalone) The remote must also run standalone (our shells do)
    Don't share at all Each app needs its own instance (axios with own interceptors, own Vuex store) –

    name: 'retry-plugin',

        try {

    #7. Error reference: every coded error

    Runtime errors look like:

    text
    [ Federation Runtime ]: Failed to load script resources. #RUNTIME-008
args: {"remoteName":"…","resourceUrl":"http://localhost:8080/remoteEntry.js"}
View the docs to see how to solve: https://module-federation.io/guide/troubleshooting/runtime#runtime-008

    Read args: it names the remote and the URL that failed.

    #RUNTIME-001: Failed to get remoteEntry exports

    Cause: remoteEntry.js loaded, but didn't export a container (get/init). Usually the URL returns something else: the host's index.html (SPA fallback), a 404 page, or a var entry loaded as type: 'module'. Fix:

    1. Open the entry URL directly in the browser and check it's JavaScript.
    2. Match the type: Vite remotes are 'module', webpack/rspack are 'var'.
    3. Check filename in the remote equals the file name in the host's URL.

    #RUNTIME-002: The remote entry interface does not contain "init"

    Cause: the loaded file isn't a federation container, or two different runtimes are mixed (very old webpack MF 1 container without init, or a wrong entryGlobalName). Fix: for var remotes make entryGlobalName equal the remote's name. Rebuild the remote with a current plugin. Don't point entry at a regular app bundle.

    #RUNTIME-003: Failed to get manifest

    Cause: entry ends in .json (manifest mode) and the fetch failed or returned non-JSON. Fix: enable manifest: true in the remote, deploy mf-manifest.json, check CORS and the URL. Or point entry at remoteEntry.js instead.

    #RUNTIME-004: Failed to locate remote

    Cause: import('shellX/App') (or loadRemote) uses a remote name that isn't registered. Typo, or the remote was not added to remotes. Fix: the prefix before / must equal a key in remotes. Restart the dev server after changing remotes.

    #RUNTIME-005: Invalid loadShareSync function call from bundler runtime

    Cause: a shared module was needed synchronously (at module evaluation time) before the share scope was ready. Typical with eager mismatches or code that reads a shared lib in a top-level statement of the entry. Fix: keep the share async (no eager), or make the consumer await something first. Ensure the host init script runs before the entry (hostInitInjectLocation: 'html').

    #RUNTIME-006: Invalid loadShareSync function call from runtime

    Cause: same as 005, but triggered through the runtime API (loadShareSync). Fix: use await loadShare(...), or provide the dependency eagerly in the host.

    #RUNTIME-007: Failed to get remote snapshot

    Cause: manifest/snapshot mode couldn't resolve the remote's snapshot (manifest unreachable, or DevTools override pointing to a dead URL). Fix: check the manifest URL, clear Module Federation DevTools overrides, or set disableSnapshot only if you never use manifests.

    #RUNTIME-008: Failed to load script resources

    The most common one. The browser couldn't load remoteEntry.js or a chunk.

    Cause How to see it Fix in this repo
    Remote not running Network tab: ERR_CONNECTION_REFUSED npm run dev at the root (starts all three)
    CORS Console: blocked by CORS policy Add the loading page's origin to the remote's VITE_CORS_ORIGINS
    Wrong URL 404 on remoteEntry.js Fix VITE_SHELL_*_ENTRY / VITE_HOST_ENTRY in .env.[mode]
    Preview using production URLs requests to example.com Use npm run preview (runs --mode localprod)
    Mixed content HTTPS page loading HTTP remote Serve remotes over HTTPS
    CSP Refused to load the script Allow remote origins in script-src
    Blocked host 403 Blocked request. This host is not allowed Add it to VITE_ALLOWED_HOSTS
    macOS AirPlay on :5000 403 with no Vite page Don't use port 5000 on macOS (this repo uses 8080–8082)
    Standalone remote, host down :8080/remoteEntry.js fails from :8081 Start the host (remotes need host/ui-dev)

    #RUNTIME-009: Please call createInstance first

    Cause: runtime API (loadRemote, registerRemotes) used before the federation instance exists, often in code that runs before the host init script, or from a second copy of @module-federation/runtime. Fix: call it after app start, use getInstance(), and make sure only one runtime package version is installed (npm ls @module-federation/runtime).

    #RUNTIME-010: The name option cannot be changed after initialization

    Cause: init() / createInstance() called again with a different name. Fix: keep one instance per container. For a separate one, use createInstance({ name }).

    #RUNTIME-011: The remoteEntry URL is missing from the remote snapshot

    Cause: manifest exists but has no remoteEntry (the remote was built with experiments.hostProvidesAllShared or a broken manifest). Fix: rebuild the remote with a normal filename, or use the matching host mode.

    #RUNTIME-012: The getter for the shared module is not a function

    Cause: a share is configured with import: false (no local fallback) and nobody provided it at runtime, e.g. a remote running standalone while expecting the host's copy. Fix: remove import: false, or make sure the providing container loads first. In this repo vue keeps a local fallback, so remotes run standalone.

    #RUNTIME-013: The manifest is not a valid Module Federation manifest

    Cause: the .json at entry isn't an mf-manifest.json (wrong file, HTML error page, or an old format). Fix: point to the real manifest from a current build, or to remoteEntry.js.

    #RUNTIME-014: The remote does not expose the requested module

    Cause: import('shellA/Foo') but exposes has no ./Foo. Or the remote was redeployed without it. Fix: compare the path after the remote name with the keys in exposes (shared.federation.json). Keys need the leading ./, imports don't.

    #RUNTIME-015: Remote container initialization failed

    Cause: the remote's init() threw: its own share scope negotiation failed, a top-level error in an exposed module's dependencies, or an incompatible runtime version. Fix: open the remote standalone to see its own error. Align @module-federation/vite versions across apps. Check requiredVersion/strictVersion of shared deps.

    #TYPE-001: Failed to generate type declaration

    Cause: dts is enabled but there's no valid tsconfig.json (this repo is plain JS). Fix: set dts: false (done in every app), or add a tsconfig.json if you move to TS.

    #BUILD-001: Failed to find expose module

    Cause: an exposes value points to a file that doesn't exist. Fix: paths are relative to the app root, e.g. ./src/expose/App.mjs. Check the extension (.mjs vs .js).

    #BUILD-002: PublicPath is required in prod mode

    Cause: production build without a usable public path. Fix: set an absolute Vite base (this repo: VITE_PUBLIC_URL) or the publicPath option.

    #9. Debugging workflow

    1. Network tab, filter remoteEntry: is each entry 200 and JavaScript?
    2. Console: read the #RUNTIME-0xx code and its args, then look it up above.
    3. Open the remote standalone (http://localhost:8081): if it fails there, it's the remote's bug, not federation.
    4. globalThis.__FEDERATION__ in the console: check registered remotes, share scope and which vue version was picked.
    5. Check env: every app prints its resolved env on start (env mode … remote:host …).
    6. Clean caches: npm run clean, then restart (removes dist/ and .__mf__temp).

    #10. Production checklist

    • Absolute VITE_PUBLIC_URL per app and environment
    • VITE_CORS_ORIGINS lists every origin that loads the app (remotes ↔ host for ui-dev)
    • remoteEntry.js served with no-cache; assets/* with long-lived caching
    • HTTPS everywhere (no mixed content), CSP script-src includes remote origins
    • Deploy order: remotes, then host. ui-dev and exposed APIs stay backward compatible
    • shareStrategy: 'loaded-first', vue singleton, nothing else shared unless required
    • Error boundary for every remote (defineRemoteComponent), optional retry plugin

    #1. Module Federation

    Plugin: @module-federation/vite (Module Federation 2.0 runtime, maintained by the Module Federation org and recommended by the Vite team). Unlike the older @originjs/vite-plugin-federation, remotes work in dev mode, so you get HMR in every app while running the host.

    Federation runs both ways:

    App Exposes Consumes
    host ./ui-dev (shared UI library) shellA/App, shellB/App
    shell-a ./App host/ui-dev
    shell-b ./App host/ui-dev

    Remotes read their options from shared.federation.json (see How vite.config.mjs is built):

    json
    {
  "name": "shellA",
  "exposes": { "./App": "./src/expose/App.mjs" },
  "remotes": { "host": { "type": "module", "entryEnv": "VITE_HOST_ENTRY" } },
  "shared": { "vue": { "singleton": true, "requiredVersion": "^3.5.0" } },
  "bundleAllCSS": true,
  "shareStrategy": "loaded-first"
}

    Host keeps its options inline in apps/host/vite.config.mjs:

    js
    federation({
  name: 'host',
  exposes: { './ui-dev': './src/ui-dev/index.mjs' },
  remotes: {
    shellA: { type: 'module', name: 'shellA', entry: env.raw.VITE_SHELL_A_ENTRY, entryGlobalName: 'shellA' },
    shellB: { type: 'module', name: 'shellB', entry: env.raw.VITE_SHELL_B_ENTRY, entryGlobalName: 'shellB' },
  },
  shared: { vue: { singleton: true, requiredVersion: '^3.5.0' } },
  bundleAllCSS: true,
  shareStrategy: 'loaded-first',
})

    The host imports shellA/App like a normal module. src/utils/defineRemoteComponent.mjs wraps it in defineAsyncComponent with loading and error components, so a remote that is down shows a friendly card instead of breaking the page.

    shareStrategy: 'loaded-first' stops the runtime from fetching every remote's remoteEntry.js up front. Without it, a standalone shell-b that loads host/ui-dev would also try to fetch shell-a.

    #Shared UI library

    See ui-dev. Remotes write <UiButton> with no import, and a components resolver turns it into import { UiButton } from 'host/ui-dev'. Each remote's exposed entry (src/expose/App.mjs) awaits host/ui-dev before the host renders it.

    #What is shared and why

    Package / module Shared? Reason
    vue ✅ singleton Remotes render inside the host's Vue app; two Vue runtimes would break reactivity and provide/inject.
    host/ui-dev ✅ exposed module One component library, owned and served by the host.
    vue-router ❌ Only the host routes. Remotes expose components, not routers.
    vuex ❌ Each app must own its store and its Vuex version.
    axios ❌ Each app owns its HTTP client, interceptors and defaults (requirement).

    #2. Independent Vuex stores

    Because remotes render inside the host's Vue app, a bare useStore() in a remote would resolve the host's store (or nothing). To keep stores isolated:

    1. Every app creates its store and its own injection key: hostStoreKey, shellAStoreKey, shellBStoreKey (src/store/index.mjs).
    2. The host installs its store with app.use(store, hostStoreKey).
    3. Each remote's root App.vue calls provide(shellAStoreKey, store), so its whole subtree resolves its own store, both inside the host and standalone.
    4. Components use auto-imported helpers: useHostStore(), useShellAStore(), useShellBStore() (src/composables).

    All modules are namespaced: true.

    #3. Private axios instances

    src/services/http.mjs exists in every app and calls axios.create():

    App baseURL (dev) timeout Header
    host https://dummyjson.com VITE_API_TIMEOUT (10s) X-Client-App: host
    shell-a https://dummyjson.com 8s X-Client-App: shell-a
    shell-b https://jsonplaceholder.typicode.com 8s X-Client-App: shell-b

    Every instance also sends its own API gateway key (x-api-gateway-key, different per app and per environment), and mock requests are answered by an axios adapter that verifies that key first. See ENVIRONMENTS.md.

    Interceptors are per instance. The global axios default instance is never configured, and axios is not in shared, so every bundle carries its own copy.

    #4. Authentication contract

    • The host logs in (store/modules/auth.mjs → services/authService.mjs).
    • The session { user, token } is written to sessionStorage['mfe.auth'].
    • Each remote's axios request interceptor reads the token from that key and sends Authorization: Bearer <token>.
    • The host also passes user as a prop to each remote root component.
    • Login/logout broadcasts mfe:auth-changed.

    Mock login: demo / demo123, guest / guest123. Set VITE_USE_MOCK_AUTH=false to use the real dummyjson endpoint (emilys / emilyspass).

    #5. Event bus (src/utils/mfeBus.mjs, one copy per app)

    Event Publisher → Subscriber Payload
    mfe:auth-changed host → remotes { user }
    mfe:cart-updated shell-a → host { count, items[] }
    mfe:tasks-updated shell-b → host { open, total }

    The host listens in App.vue and commits into its notifications module, which drives the header badges and dashboard cards.

    #6. Styling

    • index.html of each app carries inline critical CSS (background, font, splash). Remote index.html files are only used standalone, so their inline CSS never reaches the host.
    • src/styles/_tokens.scss holds variables, mixins and functions only, injected into every <style lang="scss"> via css.preprocessorOptions.scss.additionalData.
    • Remote components are scoped and namespaced by a root class (.shell-a, .shell-b). With bundleAllCSS: true all CSS imported by a remote ships with ./App, so keep global selectors out of remotes. Standalone-only layout lives inline in index.html.

    #7. Failure isolation

    • Remote unreachable → RemoteFallback error card (host keeps working).
    • Host unreachable → standalone remotes can't load host/ui-dev (run the host too).
    • API unreachable → the remote's service falls back to src/services/fixtures.
    • Remote throws during render → only that route's view is affected.

    #5. No TypeScript

    • All source and config files are .mjs / .vue with <script setup> in JavaScript.
    • unplugin-auto-import and unplugin-vue-components run with dts: false, so no .d.ts files are generated.
    • jsconfig.json in each app gives editors the @/* alias and ESM resolution; it does not type-check (checkJs: false).
    • Federated type generation is off (dts: false in the federation options).

    #6. Why .mjs

    .mjs is always ESM in Node, independent of "type" in package.json, so config files, scripts (scripts/build-docs.mjs) and source files all share one unambiguous module format. Vite resolves .mjs by default (resolve.extensions starts with .mjs), so imports can stay extension-less: import { http } from './http' finds http.mjs.

    #Why the remotes await import('host/ui-dev') first

    host/ui-dev is a federated module, so it arrives asynchronously. A component whose setup() runs before it has arrived would see UiButton === undefined. Both entry points of a remote therefore wait for it:

    • src/expose/App.mjs (what the host imports as shellA/App): await import('host/ui-dev'), then re-exports App.vue.
    • src/main.mjs (standalone): await import('host/ui-dev') before createApp().mount().

    Vite 7 guide (with examples from this repo)

    Vite 7 was released in June 2025. It is an evolutionary release: the config format is the same as Vite 5/6, but the platform baseline moved forward. This guide covers what you need to run, configure and reason about the apps in this repo.

    #1. Requirements and what changed in 7

    Topic Vite 7
    Node.js 20.19+ or 22.12+ (Node 18 dropped). These versions can require() ESM, so Vite ships as ESM only.
    Default build.target 'baseline-widely-available' (Chrome/Edge 107, Firefox 104, Safari 16). Was 'modules'.
    Sass Only the modern Sass API is supported. The legacy API (api: 'legacy') was removed.
    Removed splitVendorChunkPlugin, hook-level enforce / transform in transformIndexHtml (use order / handler).
    Environment API Still experimental; adds a buildApp hook for frameworks. Not needed for SPAs.
    Bundler Rollup 4 for builds, esbuild for dep pre-bundling. Rolldown is available as the drop-in rolldown-vite package (and is the default in Vite 8).
    Plugin Vue @vitejs/plugin-vue@6 supports Vite 5 → 8.
    Vitest Use Vitest 3.2+ with Vite 7.

    In this repo every app sets build.target: 'esnext', because the Module Federation runtime uses top-level await.

    #2. How Vite works (vs. a bundler-first dev server)

    • Dev: Vite serves your source as native ES modules. Only the file the browser asks for is transformed (.vue → JS, .scss → CSS). Dependencies in node_modules are pre-bundled once with esbuild into node_modules/.vite. Start-up time doesn't grow with app size, and HMR only touches the edited module.
    • Build: Rollup bundles, tree-shakes, code-splits and hashes for production.

    #3. Project anatomy

    text
    apps/host/
├─ index.html        ← the real entry (not in /public). Vite parses it and follows <script type="module">
├─ public/           ← copied as-is, served at /  (favicon.svg)
├─ vite.config.mjs
├─ .env*             ← env files
└─ src/main.mjs

    index.html supports env replacement: <title>%VITE_APP_TITLE%</title>.

    #4. The config, line by line (apps/host/vite.config.mjs)

    js
    export default defineConfig(({ command, mode }) => {   // function form gives command/mode
  const env = readEnv(mode, root, ['VITE_SHELL_A_ENTRY', 'VITE_SHELL_B_ENTRY'])
  //          └─ config/env.mjs: loadEnv(mode, root, '') + validation + typed values
  return {
    base: command === 'build' ? env.publicUrl : '/',
    plugins: [envBanner(env, remoteUrls), vue(), AutoImport({...}), Components({...}), federation({...})],
    resolve: { alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) } },
    define:  { __APP_NAME__: JSON.stringify(env.appName), __APP_ENV__: JSON.stringify(env.appEnv) },
    css:     { preprocessorOptions: { scss: { additionalData: `@use "@/styles/tokens" as *;\n` } } },
    server:  { host: env.devHost, port: env.port, strictPort: true, open: env.open, origin: env.origin, cors: { origin: env.corsOrigins } },
    preview: { host: env.devHost, port: env.port, strictPort: true, cors: { origin: env.corsOrigins } },
    esbuild: { pure: env.dropConsole ? ['console.log', 'console.debug'] : [] },
    build:   { target: 'esnext', sourcemap: env.sourcemap },
  }
})
    • command is 'serve' or 'build'; every app uses it to set an absolute base only for builds.
    • mode is development for vite, production for vite build, or whatever --mode says.
    • The config file is vite.config.mjs: always ESM, no TypeScript. Details in VITE_CONFIG.md.

    #5. Environment variables

    • In vite.config.mjs use loadEnv(mode, root, '') (this repo wraps it in config/env.mjs). import.meta.env is not available inside the config.
    • import.meta.env.VITE_* in client code; MODE, DEV, PROD, BASE_URL, SSR are built in.
    • Files: .env, .env.local, .env.[mode], .env.[mode].local. See ENVIRONMENTS.md.
    • process.env does not exist in browser code. Replace process.env.VUE_APP_X with import.meta.env.VITE_X.

    #6. CSS and Sass

    • Install sass (or sass-embedded, faster) and use <style lang="scss">. No loader config.
    • Vite 7 uses the modern compiler API: use @use / @forward, sass:map, sass:color. @import and global functions like map-get still compile but print deprecation warnings.
    • additionalData prepends code to every Sass file. Put only variables, mixins and functions there, never real CSS rules, or they get duplicated per component.
    • CSS Modules: name files *.module.scss. PostCSS: add postcss.config.js, it's picked up automatically.
    • Inline <style> in index.html is left as-is: ideal for critical CSS (see each app's index.html).

    #7. Static assets

    • import logo from './logo.png' gives a hashed URL. ?raw, ?url, ?inline, ?worker suffixes are available.
    • Files in public/ are referenced by absolute path (/favicon.svg) and not hashed.
    • new URL('./img.png', import.meta.url).href works for dynamic paths.

    #8. Auto import (unplugin)

    js
    AutoImport({
  imports: [
    'vue', 'vue-router', 'vuex',            // ref, computed, useRoute, useStore…
    { 'lodash-es': [['default', '_']] },    // `_` → import _ from 'lodash-es'
  ],
  include: [/\.[cm]?[jt]sx?$/, /\.vue$/, /\.vue\?vue/], // also .mjs files (store modules)
  dirs: ['src/composables', 'src/utils'],   // your own exports become globals too
  dts: false,                               // plain JS: no .d.ts (set a path to generate one)
  vueTemplate: true,                        // also usable inside <template>
})
Components({ dirs: ['src/components'], dts: false })

    #lodash as _

    Every app has lodash-es as its own dependency (not federated, see notShared in the remotes' shared.federation.json) and gets _ without an import line:

    js
    // apps/shell-a/src/store/modules/cart.mjs
count: (s) => _.sumBy(s.lines, 'qty'),
total: (s) => _.round(_.sumBy(s.lines, (l) => l.qty * l.price), 2),
REMOVE(state, id) { state.lines = _.reject(state.lines, { id }) },

// apps/shell-a/src/components/SearchBar.vue
const search = _.debounce((q) => store.dispatch('catalog/fetch', _.trim(q)), 300)
watch(query, search)
onBeforeUnmount(() => search.cancel())

    Other uses: _.startCase / _.compact (host auth/displayName), _.get / _.capitalize (host Home), _.countBy / _.filter / _.find (shell-b tasks store), _.truncate / _.upperFirst (shell-b TaskItem).

    Gotchas:

    • Don't use _ inside <template>. Vue's component proxy has its own _ property (the internal instance), so {{ _.truncate(x) }} fails with upperFirst is not a function. Wrap it in a computed in <script setup> instead.
    • The default include of unplugin-auto-import doesn't match .mjs. This repo adds /\.[cm]?[jt]sx?$/ so _ (and ref, computed, …) work in .mjs store modules too.
    • import _ from 'lodash-es' pulls in all of lodash (about 25 kB gzip per app). If bundle size matters, auto-import named functions instead: { 'lodash-es': ['debounce', 'sumBy'] }.

    Keep entry files (main.mjs) explicit: it makes bootstrap code readable.

    This repo runs both plugins with dts: false (no TypeScript). Components can also come from a resolver: the remotes map every <UiXxx> tag to the federated module host/ui-dev:

    js
    Components({ resolvers: [(name) => (/^Ui[A-Z]/.test(name) ? { name, from: 'host/ui-dev' } : undefined)] })

    #9. Code splitting

    • () => import('./View.vue') in routes creates a separate chunk.
    • build.rollupOptions.output.manualChunks replaces the removed splitVendorChunkPlugin if you need vendor chunks.

    #10. Dev server and preview

    • server.port, server.strictPort, server.proxy (replace webpack-dev-server proxy), server.origin (absolute asset URLs; the remotes use it so the host can load their dev modules), server.cors (Vite 6+ restricts CORS to localhost origins by default; remotes enable it explicitly).
    • vite preview serves dist/ for a local production check. It is not a production server.

    #11. Module Federation in Vite 7

    See ARCHITECTURE.md. Key points:

    • @module-federation/vite supports Vite 5 through 8, dev + build.
    • Remotes need an absolute base in production (VITE_PUBLIC_URL) and server.origin in dev.
    • Use type: 'module' for Vite remotes. Use type: 'var' only for webpack/rspack remotes.
    • bundleAllCSS: true makes a remote's CSS load with its exposed module.

    #12. Upgrading an existing Vite 5/6 app to 7

    1. Upgrade Node to 22 LTS (or 20.19+).
    2. npm i -D vite@^7 @vitejs/plugin-vue@^6.
    3. Remove css.preprocessorOptions.scss.api: 'legacy' if present and fix Sass deprecations.
    4. Remove splitVendorChunkPlugin (use manualChunks).
    5. If you must support older browsers than Safari 16 / Chrome 107, set build.target explicitly or use @vitejs/plugin-legacy.
    6. Check plugins declare vite@^7 in peer dependencies.

    #0. Strategy

    Migrate one app at a time, remotes first or host first, never big-bang. With Module Federation 2.0 a Vite host can consume webpack remotes and vice versa (see step 9), so the system keeps working while apps move over.

    Recommended order:

    1. Upgrade the webpack app to Vue 3.5 and Node 22 first (no build changes).
    2. Migrate one leaf remote (fewest dependents) to Vite.
    3. Migrate the remaining remotes.
    4. Migrate the host last.

    #8. Vuex and axios in a micro-frontend

    These don't change between bundlers, but migrating is a good moment to fix two common webpack-era MFE problems:

    1. Shared store by accident. If vuex was shared: { vuex: { singleton: true } } and remotes called useStore(), they could get the host's store. Use one store per app with its own injection key and provide it from the remote root (apps/shell-a/src/App.vue).
    2. Global axios defaults. axios.defaults.baseURL = ... in one app leaks into others when axios is shared. Use axios.create() per app and remove axios from shared (apps/*/src/services/http.mjs).

  shellA: { type: 'module', name: 'shellA', entry: 'http://localhost:8081/remoteEntry.js', entryGlobalName: 'shellA' },

    #Bootstrap file

    webpack MF needs an async boundary (main.js → import('./bootstrap')) to avoid "Shared module is not available for eager consumption". Delete it in Vite: the plugin initialises sharing before your entry runs. Put the code back in main.mjs.

    #Mixed bundlers during migration

    • Vite host → webpack remote: declare the remote with type: 'var' and its global name.
    • webpack host → Vite remote: add varFilename: 'varRemoteEntry.js' to the Vite remote and point the webpack host at that file (shellA@https://.../varRemoteEntry.js).
    • Keep shared versions compatible on both sides.

    #Shared UI kit

    webpack MFE setups often share a design-system package (shared: { '@acme/ui': { singleton: true } }) or publish it to npm. Here the host exposes it instead (exposes: { './ui-dev': … }), and remotes consume host/ui-dev through a components resolver. That means no npm release, one version in production, and themes through CSS variables. See ui-dev.

    #Moving federation options out of the config (remotes)

    Remotes keep their ModuleFederationPlugin fields in shared.federation.json (name, exposes, remotes, shared). Remote URLs become env key names (entryEnv), so one JSON file works for every environment. See How vite.config.mjs is built.

    #10. JavaScript only, as .mjs

    • Rename vue.config.js / webpack.config.js to vite.config.mjs. .mjs is always ESM, so import/export work whatever "type" says.
    • Rename source files to .mjs (main.mjs, router/index.mjs, …) and update <script type="module" src="/src/main.mjs">. Extension-less imports keep working because Vite resolves .mjs first.
    • Drop TypeScript-only tooling: set dts: false for unplugin-auto-import/-components and federation, delete generated .d.ts, and add a jsconfig.json for editor path aliases.
    • Replace process.env in config code with loadEnv(mode, root, '') (see config/env.mjs).

    #11. Testing

    jest + vue-jest → Vitest (npm i -D vitest @vue/test-utils jsdom). It reuses vite.config.mjs (aliases, plugins). Most Jest APIs work with vi instead of jest.
