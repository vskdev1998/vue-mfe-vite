    vue-mfe-vite

    A complete, working Vue 3 + Vite 7 micro-frontend monorepo built with Module Federation.

    App Role Port Exposes / consumes Theme
    apps/host Container: routing, login, layout, header 5000 consumes shellA/App, shellB/App green
    apps/shell-a Remote: product catalog + cart 5001 exposes ./App indigo
    apps/shell-b Remote: task board 5002 exposes ./App teal

    #What's inside

    • Vite 7 (vite@^7.3) with @vitejs/plugin-vue@6
    • Module Federation via @module-federation/vite (works in dev and build)
    • Sass (modern compiler API) with per-app design tokens injected through additionalData
    • Critical CSS inline in each index.html (background + boot splash before JS loads)
    • Auto import: unplugin-auto-import (vue, vuex, vue-router, own composables) and unplugin-vue-components (no manual component registration)
    • Vuex 4: one independent store per app, each installed/provided under its own injection key
    • axios: one private instance per app (own baseURL, timeout, interceptors) and not shared through federation
    • Sample login in the host (route guard, session in sessionStorage)
    • Cross-app communication with a tiny window CustomEvent bus (mfe:*) instead of shared state
    • Per-app env files for development / localprod / staging / production
    • Offline fixtures, so the demo still works behind a proxy with no internet

    #Quick start

    Requirements: Node 20.19+ or 22.12+ (Vite 7 requirement) and npm 10+.

    bash
    npm install          # installs all three workspaces
npm run dev          # starts host :5000, shell-a :5001, shell-b :5002 together

    Open http://localhost:5000 and sign in with demo / demo123 (or guest / guest123).

    Each remote also runs on its own: http://localhost:5001 and http://localhost:5002.

    #Troubleshooting

    Symptom Fix
    "Shell A is unavailable" card in the host The remote isn't running. npm run dev at the root starts all apps. Check VITE_SHELL_A_ENTRY.
    Port already in use Ports are strictPort. Free 5000–5002 or change VITE_PORT (and the host's VITE_SHELL_*_ENTRY).
    Remote chunks 404 in production The remote's VITE_PUBLIC_URL (build base) must be the URL it is deployed at.
    Products / tasks show fixture data The public APIs (dummyjson / jsonplaceholder) were unreachable; the services fell back to src/services/fixtures.
    Unsupported engine / Vite won't start Upgrade Node to 20.19+ or 22.12+.

    #1. Module Federation

    Plugin: @module-federation/vite (Module Federation 2.0 runtime, maintained by the Module Federation org and recommended by the Vite team). Unlike the older @originjs/vite-plugin-federation, remotes work in dev mode, so you get HMR in every app while running the host.

    Remotes (apps/shell-*/vite.config.js):

    js
    federation({
  name: 'shellA',                 // container name, must be unique
  filename: 'remoteEntry.js',     // served at <VITE_PUBLIC_URL>/remoteEntry.js
  exposes: { './App': './src/App.vue' },
  shared: { vue: { singleton: true, requiredVersion: '^3.5.0' } },
  bundleAllCSS: true,             // inject this remote's CSS when the host loads ./App
  dts: false,                     // plain JS project
})

    Host (apps/host/vite.config.js):

    js
    federation({
  name: 'host',
  remotes: {
    shellA: { type: 'module', name: 'shellA', entry: env.VITE_SHELL_A_ENTRY, entryGlobalName: 'shellA', shareScope: 'default' },
    shellB: { type: 'module', name: 'shellB', entry: env.VITE_SHELL_B_ENTRY, entryGlobalName: 'shellB', shareScope: 'default' },
  },
  shared: { vue: { singleton: true, requiredVersion: '^3.5.0' } },
})

    The host imports shellA/App like a normal module. src/utils/defineRemoteComponent.js wraps it in defineAsyncComponent with loading and error components, so a remote that is down shows a friendly card instead of breaking the page.

    #What is shared and why

    Package Shared? Reason
    vue ✅ singleton Remotes render inside the host's Vue app; two Vue runtimes would break reactivity and provide/inject.
    vue-router ❌ Only the host routes. Remotes expose components, not routers.
    vuex ❌ Each app must own its store and its Vuex version.
    axios ❌ Each app owns its HTTP client, interceptors and defaults (requirement).

    #2. Independent Vuex stores

    Because remotes render inside the host's Vue app, a bare useStore() in a remote would resolve the host's store (or nothing). To keep stores isolated:

    1. Every app creates its store and its own injection key: hostStoreKey, shellAStoreKey, shellBStoreKey (src/store/index.js).
    2. The host installs its store with app.use(store, hostStoreKey).
    3. Each remote's root App.vue calls provide(shellAStoreKey, store), so its whole subtree resolves its own store, both inside the host and standalone.
    4. Components use auto-imported helpers: useHostStore(), useShellAStore(), useShellBStore() (src/composables).

    All modules are namespaced: true.

    #3. Private axios instances

    src/services/http.js exists in every app and calls axios.create():

    App baseURL (dev) timeout Header
    host https://dummyjson.com VITE_API_TIMEOUT (10s) X-Client-App: host
    shell-a https://dummyjson.com 8s X-Client-App: shell-a
    shell-b https://jsonplaceholder.typicode.com 8s X-Client-App: shell-b

    Interceptors are per instance. The global axios default instance is never configured, and axios is not in shared, so every bundle carries its own copy.

    #4. Authentication contract

    • The host logs in (store/modules/auth.js → services/authService.js).
    • The session { user, token } is written to sessionStorage['mfe.auth'].
    • Each remote's axios request interceptor reads the token from that key and sends Authorization: Bearer <token>.
    • The host also passes user as a prop to each remote root component.
    • Login/logout broadcasts mfe:auth-changed.

    Mock login: demo / demo123, guest / guest123. Set VITE_USE_MOCK_AUTH=false to use the real dummyjson endpoint (emilys / emilyspass).

    #5. Event bus (src/utils/mfeBus.js, one copy per app)

    Event Publisher → Subscriber Payload
    mfe:auth-changed host → remotes { user }
    mfe:cart-updated shell-a → host { count, items[] }
    mfe:tasks-updated shell-b → host { open, total }

    The host listens in App.vue and commits into its notifications module, which drives the header badges and dashboard cards.

    #6. Styling

    • index.html of each app carries inline critical CSS (background, font, splash). Remote index.html files are only used standalone, so their inline CSS never reaches the host.
    • src/styles/_tokens.scss holds variables, mixins and functions only, injected into every <style lang="scss"> via css.preprocessorOptions.scss.additionalData.
    • Remote components are scoped and namespaced by a root class (.shell-a, .shell-b). With bundleAllCSS: true all CSS imported by a remote ships with ./App, so keep global selectors out of remotes. Standalone-only layout lives inline in index.html.

    #7. Failure isolation

    • Remote unreachable → RemoteFallback error card (host keeps working).
    • API unreachable → the remote's service falls back to src/services/fixtures.
    • Remote throws during render → only that route's view is affected.

    Environments & env files

    Every app has the same set of files:

    File Loaded when Purpose
    .env always Values common to all modes (name, title, port, timeout)
    .env.development vite / npm run dev Local dev servers, localhost remote URLs
    .env.localprod vite build --mode localprod Production bundles that still point at localhost (for vite preview)
    .env.staging vite build --mode staging Staging domains / CDN
    .env.production vite build Production domains / CDN
    .env.example never (documentation) Every variable with a comment
    .env.[mode].local that mode, on your machine Personal overrides, git-ignored

    Priority (later wins): .env < .env.local < .env.[mode] < .env.[mode].local < real shell environment variables.

    Only variables prefixed with VITE_ reach browser code (import.meta.env.VITE_*). Never put secrets in these files: everything VITE_* ends up in the JS bundle.

    #Host (apps/host)

    Variable development localprod staging production
    VITE_APP_NAME host host host host
    VITE_PORT 5000 5000 5000 5000
    VITE_PUBLIC_URL http://localhost:5000/ http://localhost:5000/ https://staging.example.com/ https://app.example.com/
    VITE_API_BASE_URL https://dummyjson.com https://dummyjson.com https://api.staging.example.com https://api.example.com
    VITE_SHELL_A_ENTRY http://localhost:5001/remoteEntry.js same https://shell-a.staging.example.com/remoteEntry.js https://shell-a.example.com/remoteEntry.js
    VITE_SHELL_B_ENTRY http://localhost:5002/remoteEntry.js same https://shell-b.staging.example.com/remoteEntry.js https://shell-b.example.com/remoteEntry.js
    VITE_USE_MOCK_AUTH true true false false
    VITE_API_TIMEOUT 10000 (from .env)

    vite.config.js reads VITE_SHELL_*_ENTRY with loadEnv() and fails the build if one is missing for the current mode.

    #Remotes (apps/shell-a, apps/shell-b)

    Variable development localprod staging production
    VITE_PORT 5001 / 5002 same same same
    VITE_PUBLIC_URL http://localhost:500x/ http://localhost:500x/ https://shell-x.staging.example.com/ https://shell-x.example.com/
    VITE_API_BASE_URL dummyjson (A) / jsonplaceholder (B) same same same
    VITE_HOST_URL http://localhost:5000/ same https://staging.example.com/ https://app.example.com/
    VITE_USE_MOCK_API false false false false
    VITE_API_TIMEOUT 8000 (from .env)

    VITE_PUBLIC_URL is the most important remote variable:

    • dev: becomes server.origin, so the remote's dev assets are requested from :5001 even though the page is the host on :5000.
    • build: becomes Vite's base. remoteEntry.js imports its chunks relative to this URL. If it's wrong, the host loads remoteEntry.js and then 404s on every chunk.

    #Deploying to real environments

    1. Replace example.com URLs in .env.staging / .env.production of all three apps.
    2. Build and deploy the remotes first (npm run build:staging -w @mfe/shell-a, …).
    3. Build and deploy the host.
    4. Remotes must send CORS headers allowing the host origin for remoteEntry.js and chunks (Access-Control-Allow-Origin), or be served from the same domain under different paths, e.g. https://app.example.com/mfe/shell-a/ (then use that as VITE_PUBLIC_URL).
    5. Serve remoteEntry.js with Cache-Control: no-cache; hashed chunks can be cached forever.

    Vite 7 guide (with examples from this repo)

    Vite 7 was released in June 2025. It is an evolutionary release: the config format is the same as Vite 5/6, but the platform baseline moved forward. This guide covers what you need to run, configure and reason about the apps in this repo.

    #1. Requirements and what changed in 7

    Topic Vite 7
    Node.js 20.19+ or 22.12+ (Node 18 dropped). These versions can require() ESM, so Vite ships as ESM only.
    Default build.target 'baseline-widely-available' (Chrome/Edge 107, Firefox 104, Safari 16). Was 'modules'.
    Sass Only the modern Sass API is supported. The legacy API (api: 'legacy') was removed.
    Removed splitVendorChunkPlugin, hook-level enforce / transform in transformIndexHtml (use order / handler).
    Environment API Still experimental; adds a buildApp hook for frameworks. Not needed for SPAs.
    Bundler Rollup 4 for builds, esbuild for dep pre-bundling. Rolldown is available as the drop-in rolldown-vite package (and is the default in Vite 8).
    Plugin Vue @vitejs/plugin-vue@6 supports Vite 5 → 8.
    Vitest Use Vitest 3.2+ with Vite 7.

    In this repo every app sets build.target: 'esnext', because the Module Federation runtime uses top-level await.

    #2. How Vite works (vs. a bundler-first dev server)

    • Dev: Vite serves your source as native ES modules. Only the file the browser asks for is transformed (.vue → JS, .scss → CSS). Dependencies in node_modules are pre-bundled once with esbuild into node_modules/.vite. Start-up time doesn't grow with app size, and HMR only touches the edited module.
    • Build: Rollup bundles, tree-shakes, code-splits and hashes for production.

    #3. Project anatomy

    text
    apps/host/
├─ index.html        ← the real entry (not in /public). Vite parses it and follows <script type="module">
├─ public/           ← copied as-is, served at /  (favicon.svg)
├─ vite.config.js
├─ .env*             ← env files
└─ src/main.js

    index.html supports env replacement: <title>%VITE_APP_TITLE%</title>.

    #4. The config, line by line (apps/host/vite.config.js)

    js
    export default defineConfig(({ command, mode }) => {   // function form gives command/mode
  const env = loadEnv(mode, process.cwd(), '')          // '' = load ALL vars, not only VITE_*
  return {
    plugins: [vue(), AutoImport({...}), Components({...}), federation({...})],
    resolve: { alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) } },
    css: { preprocessorOptions: { scss: { additionalData: `@use "@/styles/tokens" as *;\n` } } },
    server:  { port, strictPort: true },
    preview: { port, strictPort: true },
    build:   { target: 'esnext' },
  }
})
    • command is 'serve' or 'build'; remotes use it to set base only for builds.
    • mode is development for vite, production for vite build, or whatever --mode says.

    #5. Environment variables

    • import.meta.env.VITE_* in client code; MODE, DEV, PROD, BASE_URL, SSR are built in.
    • Files: .env, .env.local, .env.[mode], .env.[mode].local. See ENVIRONMENTS.md.
    • process.env does not exist in browser code. Replace process.env.VUE_APP_X with import.meta.env.VITE_X.

    #6. CSS and Sass

    • Install sass (or sass-embedded, faster) and use <style lang="scss">. No loader config.
    • Vite 7 uses the modern compiler API: use @use / @forward, sass:map, sass:color. @import and global functions like map-get still compile but print deprecation warnings.
    • additionalData prepends code to every Sass file. Put only variables, mixins and functions there, never real CSS rules, or they get duplicated per component.
    • CSS Modules: name files *.module.scss. PostCSS: add postcss.config.js, it's picked up automatically.
    • Inline <style> in index.html is left as-is: ideal for critical CSS (see each app's index.html).

    #7. Static assets

    • import logo from './logo.png' gives a hashed URL. ?raw, ?url, ?inline, ?worker suffixes are available.
    • Files in public/ are referenced by absolute path (/favicon.svg) and not hashed.
    • new URL('./img.png', import.meta.url).href works for dynamic paths.

    #8. Auto import (unplugin)

    js
    AutoImport({
  imports: ['vue', 'vue-router', 'vuex'],   // ref, computed, useRoute, useStore…
  dirs: ['src/composables', 'src/utils'],   // your own exports become globals too
  dts: 'src/auto-imports.d.ts',             // editor IntelliSense (generated)
  vueTemplate: true,                        // also usable inside <template>
})
Components({ dirs: ['src/components'], dts: 'src/components.d.ts' })

    auto-imports.d.ts and components.d.ts are generated on the first dev/build. Keep entry files (main.js) explicit: it makes bootstrap code readable.

    #9. Code splitting

    • () => import('./View.vue') in routes creates a separate chunk.
    • build.rollupOptions.output.manualChunks replaces the removed splitVendorChunkPlugin if you need vendor chunks.

    #10. Dev server and preview

    • server.port, server.strictPort, server.proxy (replace webpack-dev-server proxy), server.origin (absolute asset URLs; the remotes use it so the host can load their dev modules), server.cors (Vite 6+ restricts CORS to localhost origins by default; remotes enable it explicitly).
    • vite preview serves dist/ for a local production check. It is not a production server.

    #11. Module Federation in Vite 7

    See ARCHITECTURE.md. Key points:

    • @module-federation/vite supports Vite 5 through 8, dev + build.
    • Remotes need an absolute base in production (VITE_PUBLIC_URL) and server.origin in dev.
    • Use type: 'module' for Vite remotes. Use type: 'var' only for webpack/rspack remotes.
    • bundleAllCSS: true makes a remote's CSS load with its exposed module.

    #12. Upgrading an existing Vite 5/6 app to 7

    1. Upgrade Node to 22 LTS (or 20.19+).
    2. npm i -D vite@^7 @vitejs/plugin-vue@^6.
    3. Remove css.preprocessorOptions.scss.api: 'legacy' if present and fix Sass deprecations.
    4. Remove splitVendorChunkPlugin (use manualChunks).
    5. If you must support older browsers than Safari 16 / Chrome 107, set build.target explicitly or use @vitejs/plugin-legacy.
    6. Check plugins declare vite@^7 in peer dependencies.

    Migrating from webpack (Vue CLI / webpack 5 Module Federation) to Vite 7

    This guide takes a typical Vue CLI or hand-rolled webpack 5 Vue 3 micro-frontend setup and moves it to the structure used in this repo. Each step maps a webpack concept to its Vite equivalent, with the real file from this repo as the target.

    #0. Strategy

    Migrate one app at a time, remotes first or host first, never big-bang. With Module Federation 2.0 a Vite host can consume webpack remotes and vice versa (see step 9), so the system keeps working while apps move over.

    Recommended order:

    1. Upgrade the webpack app to Vue 3.5 and Node 22 first (no build changes).
    2. Migrate one leaf remote (fewest dependents) to Vite.
    3. Migrate the remaining remotes.
    4. Migrate the host last.

    #1. Dependencies

    bash
    # remove
npm rm @vue/cli-service @vue/cli-plugin-babel @vue/cli-plugin-router @vue/cli-plugin-vuex \
  webpack webpack-cli webpack-dev-server vue-loader vue-style-loader css-loader sass-loader \
  style-loader html-webpack-plugin mini-css-extract-plugin babel-loader @babel/core \
  copy-webpack-plugin dotenv-webpack

# add
npm i -D vite@^7 @vitejs/plugin-vue@^6 sass @module-federation/vite \
  unplugin-auto-import unplugin-vue-components

    package.json scripts:

    webpack / Vue CLI Vite
    vue-cli-service serve / webpack serve vite
    vue-cli-service build / webpack --mode production vite build
    vue-cli-service build --mode staging vite build --mode staging
    (none) vite preview

    Add "type": "module" to package.json so vite.config.js can use ESM.

    #2. index.html moves to the project root

    webpack Vite
    public/index.html + HtmlWebpackPlugin index.html at app root
    <%= htmlWebpackPlugin.options.title %> %VITE_APP_TITLE%
    <%= BASE_URL %>favicon.ico /favicon.ico
    bundle injected automatically add <script type="module" src="/src/main.js"></script> yourself

    Inline critical CSS can stay in <style> inside index.html (see apps/host/index.html).

    #3. Config: vue.config.js / webpack.config.js → vite.config.js

    webpack Vite (vite.config.js)
    entry: './src/main.js' from index.html
    output.publicPath / publicPath base
    output.path / outputDir build.outDir (default dist)
    resolve.alias['@'] resolve.alias['@'] (Vue CLI added it implicitly, Vite does not)
    resolve.extensions incl. .vue Always write .vue in imports
    module.rules vue-loader @vitejs/plugin-vue
    module.rules babel-loader not needed (esbuild for TS/JSX, modern targets)
    module.rules sass/css/style-loader built in: just install sass
    css.loaderOptions.sass.additionalData css.preprocessorOptions.scss.additionalData
    file-loader / url-loader / asset modules built in; build.assetsInlineLimit
    DefinePlugin define
    devServer.port / proxy / headers server.port / server.proxy / server.headers
    devServer.historyApiFallback built in
    optimization.splitChunks build.rollupOptions.output.manualChunks
    ModuleFederationPlugin federation() from @module-federation/vite
    CopyWebpackPlugin (public) public/ folder
    require.context() import.meta.glob()

    #4. Environment variables

    webpack / Vue CLI Vite
    VUE_APP_API_URL VITE_API_BASE_URL
    process.env.VUE_APP_API_URL import.meta.env.VITE_API_BASE_URL
    process.env.NODE_ENV === 'production' import.meta.env.PROD
    process.env.BASE_URL import.meta.env.BASE_URL
    .env.development, .env.production same names, same idea

    Quick rename:

    bash
    grep -rl "process.env.VUE_APP_" src | xargs sed -i '' 's/process\.env\.VUE_APP_/import.meta.env.VITE_/g'   # macOS
# rename keys in .env* files: VUE_APP_ → VITE_

    If a library reads process.env.X at runtime, add define: { 'process.env.X': JSON.stringify(value) }.

    #5. Module syntax

    • require('./x') → import x from './x'; module.exports → export default.
    • require.context('./modules', false, /\.js$/) (common for auto-registering Vuex modules):
    js
    // webpack
const ctx = require.context('./modules', false, /\.js$/)
const modules = Object.fromEntries(ctx.keys().map((k) => [k.replace(/(\.\/|\.js)/g, ''), ctx(k).default]))

// Vite
const files = import.meta.glob('./modules/*.js', { eager: true })
const modules = Object.fromEntries(
  Object.entries(files).map(([path, m]) => [path.match(/\/(\w+)\.js$/)[1], m.default]),
)
    • Dynamic image paths: require(\@/assets/${name}.png`)→new URL(`../assets/${name}.png`, import.meta.url).href`.

    #6. Sass

    • ~ prefix for node_modules imports (@import '~bootstrap/scss/x') → drop it: @use 'bootstrap/scss/x'.
    • node-sass → sass (Dart Sass). Vite 7 only supports the modern API.
    • Move @import 'variables' to @use 'variables' as * and inject via additionalData (see apps/*/vite.config.js).
    • /deep/ and >>> → :deep(.child) in scoped styles.

    #7. Auto-imports instead of global registration

    webpack apps often register components globally in main.js (app.component('BaseButton', ...)) or with require.context. Replace with:

    js
    Components({ dirs: ['src/components'], dts: 'src/components.d.ts' })
AutoImport({ imports: ['vue', 'vue-router', 'vuex'], dirs: ['src/composables'], dts: 'src/auto-imports.d.ts' })

    You can keep explicit imports, the plugins only fill in what's missing.

    #8. Vuex and axios in a micro-frontend

    These don't change between bundlers, but migrating is a good moment to fix two common webpack-era MFE problems:

    1. Shared store by accident. If vuex was shared: { vuex: { singleton: true } } and remotes called useStore(), they could get the host's store. Use one store per app with its own injection key and provide it from the remote root (apps/shell-a/src/App.vue).
    2. Global axios defaults. axios.defaults.baseURL = ... in one app leaks into others when axios is shared. Use axios.create() per app and remove axios from shared (apps/*/src/services/http.js).

    #9. Module Federation: webpack → Vite

    #Remote

    js
    // webpack.config.js
new ModuleFederationPlugin({
  name: 'shellA',
  filename: 'remoteEntry.js',
  exposes: { './App': './src/App.vue' },
  shared: { vue: { singleton: true, requiredVersion: '^3.5.0' } },
})
output: { publicPath: 'http://localhost:5001/' }
    js
    // vite.config.js
federation({
  name: 'shellA',
  filename: 'remoteEntry.js',
  exposes: { './App': './src/App.vue' },
  shared: { vue: { singleton: true, requiredVersion: '^3.5.0' } },
  bundleAllCSS: true,
}),
base: command === 'build' ? env.VITE_PUBLIC_URL : '/',
server: { origin: 'http://localhost:5001', cors: true },
build: { target: 'esnext' },

    #Host

    js
    // webpack
remotes: { shellA: 'shellA@http://localhost:5001/remoteEntry.js' }

// vite
remotes: {
  shellA: { type: 'module', name: 'shellA', entry: 'http://localhost:5001/remoteEntry.js', entryGlobalName: 'shellA' },
}

    #Bootstrap file

    webpack MF needs an async boundary (main.js → import('./bootstrap')) to avoid "Shared module is not available for eager consumption". Delete it in Vite: the plugin initialises sharing before your entry runs. Put the code back in main.js.

    #Mixed bundlers during migration

    • Vite host → webpack remote: declare the remote with type: 'var' and its global name.
    • webpack host → Vite remote: add varFilename: 'varRemoteEntry.js' to the Vite remote and point the webpack host at that file (shellA@https://.../varRemoteEntry.js).
    • Keep shared versions compatible on both sides.

    #10. Testing

    jest + vue-jest → Vitest (npm i -D vitest @vue/test-utils jsdom). It reuses vite.config.js (aliases, plugins). Most Jest APIs work with vi instead of jest.

    Events published mfe:cart-updated → { count, items[] }
    Reads sessionStorage['mfe.auth'] (token for its axios instance)

    Keep this surface small and backwards compatible: the host and this remote deploy independently.

    Concern Where
    Product search (debounced) + grid src/components/SearchBar.vue, ProductGrid.vue, ProductCard.vue

    Offline fixtures (network fallback / VITE_USE_MOCK_API=true) src/services/fixtures/
    Event bus (own copy) src/utils/mfeBus.js
    Sass tokens src/styles/_tokens.scss
    Standalone bootstrap src/main.js (never runs inside the host)
    Inline critical CSS + standalone layout index.html (never loaded by the host)

    #Why the store is provided in App.vue

    Inside the host, this component renders in the host's Vue app. A bare useStore() would not find this remote's store. provide(shellAStoreKey, store) in the root and useStore(shellAStoreKey) in children keep the store private and identical in both modes.

    #CSS rules for remotes

    bundleAllCSS: true ships every CSS file this remote imports together with ./App. So: scoped styles only, a root class (.shell-a) on the root element, and no global selectors (body, #app) in .vue/.scss files. Standalone-only styles go inline in index.html.
